## 3. Re-screen or drop

What's stored today:
- **IndexedDB `screens`:** `ScreenRecord` = `{ id, keys, result, engine? }`.
- **`localStorage` parcel store:** `WorkingParcel`, which holds `screenIds`.
- **Export files.**

The policy, as I'd build it:

- **A stored result that isn't v3** (the v2 schema fails to parse as v3):
  - the screen record is deleted;
  - the parcel is kept (boundary, house, name, notes) and loses that screen id.
- **The message:** when this happens, History shows once: "Saved results from an older version of Parcel Screen
  were cleared. Your parcels, notes and houses are kept; each re-screens when you open it."
- **Re-screen on open:** opening a parcel with no current result runs the screen, as for a new parcel. **Proposed:**
  on open, not all at once at start-up. Re-screening a whole History at once would hit every public service for
  every parcel.
- **Drop:** a parcel is dropped only if it can't be re-screened, which in practice means a stored boundary that no
  longer parses. History then lists it in the same message: "Dropped (couldn't be re-screened): N parcels."
- **Within v3, an engine bump:** owner 2026-10-09: "re-screen on an engine bump". **Q2:** re-screen automatically
  on open, replacing today's "Screened with earlier rules — run again" note? Or keep the note and the button? My
  lean is automatic on open, with that note replaced by "Re-screened with the current rules". This is a text
  replacement under rule 7, so it needs your yes.
- **Import:** an export file's v2 results are skipped, and its parcels are imported without them. The import
  summary says so: "N saved results from an older version were skipped; those parcels re-screen when opened."
- **Tests:** a v2 record is cleared and its parcel kept; an unparseable boundary is dropped and named; an old-engine
  v3 record re-screens on open (Q2); export and import with v2 results.

## 4. The asking price

- **Storage:** `WorkingParcel.askingPrice: number | null`, in dollars. It's not in the screen result: the price can
  change while the land doesn't.
- **Where it's entered:** the parcel info panel (the acreage chip's sheet), as "Asking price $", beside the notes.
  It's saved like the notes.
- **History:** the row shows it ("$185k").
- **Export and import:** round-trip, a test pins it. A parcel already in History follows the import's existing rule:
  skipped, never overwritten, even if the file's price differs.
- **Not yet:** nothing reads it in the report. VR4's stages read it.

## 6. The steep-landing flag (owner, PR B decisions, 2026-10-10)

**Detection:**
- The router refuses a landing whose arc sits on a natural side slope over `landingMaxSideSlopeDeg` (35°).
- For the **target's scored route only**, the engine routes once more with that limit lifted, as the router report
  does today. If the lifted route uses a landing over 35°, that landing is the flag.
- **`avoided`:** true when the normal search found a route anyway, false when it found none.
- **Cost:** one more search per target, run only when the scored route has at least one switchback, or when no
  route was found. Q3: or every time? It never fires on the fixtures, so the gate is about the phone's time.

**Displays (owner's wording):**
- **The map:** a warning flag at the landing's spot (a small red-outlined triangle, like the suspect drawing), with
  a tooltip carrying the card line.
- **The card:** a line after the driveway note:
  - avoided: "A switchback near [d] ft would sit on a [N]° side slope — too steep without retaining walls; route
    goes around it";
  - not avoided: "…no route avoids it".
- **The gate panel:** the reason, only when it decides "No practical route found". The panel is VR2's, so B2 stores
  the data and VR2 shows it. **Q4:** or should B2 add a minimal gate panel now? My lean is no: VR2 builds the panel
  once, with all its gates.
- **"If a route simply goes around the steep spot, it's just a note, not a warning"**: when avoided, no flag in
  `flags` (the verdict is unchanged); when not avoided, it's part of the existing "No practical route found" warn.

**Tests:**
- A constructed DEM: a bench reachable only by a switchback on a 40° slope, one variant with a way round and one
  without.
- The fixtures: none, as the router report found.
